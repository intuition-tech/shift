# Перенос публикаций и вёрстка

Инструкция для того, кто переносит гайды со старого сайта (`/Users/arutyunov/dbdt`, Express + Pug + SCSS) на этот. Общее устройство проекта — в [README](README.md), живые образцы всех компонентов — на `/design-system/`.

Перед началом откройте 2–3 уже перенесённых гайда: [order-in-projects](src/pages/order-in-projects.html) (типовой), [saving-printed-layouts](src/pages/saving-printed-layouts.html) (ol с картинками в пунктах), [dubai-dodo-pizza-mena-2025](src/pages/dubai-dodo-pizza-mena-2025.html) (слайды, палитры, видео, page-local стили).

## Что переносим и чего не переносим

Переносится **живой** контент старой страницы, дословно, целиком.

**Не переносится:**

- закомментированные блоки Pug (`//` и `//-`) — в старых гайдах их много, иногда это половина файла;
- теги тем, подборок, авторов, хлебные крошки, блоки «Читать далее» — таких сущностей на новом сайте пока нет;
- `+es` (испанская локаль) — её не поддерживаем;
- обвязка старого шаблона: `.guide-nav-wrapper`, `.guide-body-wrapper`, `.mobile-breadcrumbs`, `block topicTags/peopleTags`.

Пустой `+en` означает «перевода нет» — тогда пишите русский текст без условия, английская страница покажет его же. Не переводите сами и не сокращайте: опечатки в исходнике тоже переносятся как есть.

## Картинки

**Не копируйте папку картинок целиком.** В папках старого сайта лежат черновики, отброшенные варианты и картинки от прошлых редакций — при копировании `cp -R` в репозиторий приезжают десятки мегабайт мусора. Копируйте ровно те файлы, на которые ссылается живая разметка.

Складывать в `static/images/<slug>/` (подпапки исходника можно сохранять), путь в разметке — `/images/<slug>/…`. Cloudinary и другие внешние URL оставляем внешними.

**Оптимизируйте до коммита.** Картинки со старого сайта неадекватны по весу: фотографии по 6000 px, которые рисуются в 460 px, фото в PNG, GIF-анимации по 8 МБ. Порядок:

```
npm run build
python3 -m http.server 8091 --directory site &   # нужен для замера
node tools/measure-images.mjs                    # с какой шириной что рисуется
python3 tools/optimize-images.py                 # ресайз + WebP + GIF → mp4
python3 tools/optimize-images.py --fix-links     # правит ссылки в разметке
npm run build
```

Что стоит за этим и что проверить руками:

- целевая ширина — **2× от фактической ширины отрисовки** (ретина). Текстовая колонка 960 px, значит потолок для картинки во всю ширину — 1920 px, а для `figure.ids__media XS` (184 px) — 368 px;
- **WebP** для фото и скриншотов, но палитровые PNG (плоская графика, интерфейс с малым числом цветов) часто уже легче WebP — скрипт такие оставляет, и это нормально;
- **GIF всегда в mp4**: те же кадры весят в 10–15 раз меньше. `<img>` заменяется на `<video src="…" autoplay loop muted playsinline>`; в медиа-контейнерах IDS видео уже стилизовано как картинка;
- `--fix-links` не видит пути, собранные шаблоном (`src="/images/x/{% if lang == 'ru' %}1.jpg{% else %}1-en.jpg{% endif %}"`) — такие правятся руками. Лучше их вовсе не писать: дублируйте целиком весь `<figure>` внутри `{% if %}`, это переживает любые автозамены.

Исходники оптимизации не храним: всё есть в старом репозитории, при необходимости пересохраним оттуда заново.

## Вёрстка

Старые классы не переносятся. Разметка собирается из компонентов IDS — их перечень с живыми образцами и списком классов на `/design-system/`. **Новый компонент сразу добавляется туда** — иначе следующий человек напишет его заново под другим именем.

Локальные компоненты живут в `static/css/components/` с префиксом `ids__`. Внутри компонента размеры в `em` (масштабируются от кегля), на уровне композиции — в `rem`. Цвет — только через семантические токены (`--ids__text`, `--shift__dodo-orange`), новые значения сперва заводятся в палитре `tokens/palette.css`, потом получают семантическое имя.

Структура публикации:

```html
<div class="ids__space XL"></div>
<article class="ids__wrapper guide">
  <div class="guide__nav"><ids-navbar></ids-navbar></div>   <!-- если есть разделы -->
  <h1>…</h1>
  <p class="ids__description">…</p>                          <!-- лид -->
  <ids-nav-item id="слаг-раздела" label="Название раздела">
    <h2 class="h3">…</h2>
    …
  </ids-nav-item>
  <div class="ids__space L"></div>
</article>
```

Якоря разделов — **осмысленные слаги** (`#small-formats`), а не порядковые номера, как в старом (`#n0`): номера ломаются при любой вставке раздела в середину.

Page-local `<style>` допустим для того, что не покрыто компонентами (специфичная таблица, подсветка сегментов), но: классы с префиксом страницы, а старые селекторы вида `.guide-body-wrapper .table-wrapper` переписываются на новые (`.guide .ids__table-wrapper`). Если то же самое понадобится второй раз — это уже компонент, заводите его в `components/`.

### Грабли, на которые уже наступали

- **Нативный CSS-нестинг не умеет конкатенацию `&---mod`** — это привычка из Sass. Модификаторы с длинными суффиксами пишутся полными селекторами (см. [no-yes.css](static/css/components/no-yes.css)); иначе правило молча не применяется.
- **Инлайн-блоки `.ids__no-yes` ставятся вплотную** — пробел между `</div>` и `<div>` считается за ширину и ломает строку. В разметке они склеиваются комментарием: `</div><!--\n  --><div…`.
- **YAML во фронтматтере**: значение с двоеточием (`description: Алгоритм: 3 шага`) роняет сборку — берите в кавычки.
- **`{% %}` исполняется и внутри HTML-комментариев** — незакрытый тег Nunjucks там сломает сборку.

## Проверка перед коммитом

```
npm run build                    # без ошибок
```

Затем на локальном сервере: битые локальные ссылки (собрать все `href`/`src` со страниц и проверить существование файлов), консоль браузера, 404 в сети, и глазами — 2–3 страницы с самыми сложными компонентами. Ссылки на ещё не перенесённые гайды в 404 — это нормально и ожидаемо, остальное — нет.

Не коммитьте `site/` (в гитигноре) и не оставляйте временные файлы в `static/`.
