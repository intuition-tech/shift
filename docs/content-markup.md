# Вёрстка публикаций

Инструкция для агента: как сверстать публикацию на новом сайте и как перенести её со старого. Общее устройство проекта — в [README](../README.md), живые образцы всех компонентов со списком классов и мест использования — на `/design-system/`.

## Структура публикации

Публикация — один файл `src/pages/<slug>.html` с фронтматтером и инлайновым переключением языка. URL плоские: `/<slug>/` и `/en/<slug>/`.

```html
---
title: Название — Shift
titleEn: Title — Shift
description: "…"
tags: publication
---
<div class="ids__space XL"></div>
<article class="ids__wrapper publication">
  <div class="publication__nav"><ids-navbar></ids-navbar></div>   <!-- если есть разделы -->
  <h1>{% if lang == 'ru' %}…{% else %}…{% endif %}</h1>
  {% include "pub-meta.html" %}                              <!-- дата и теги из src/data/publications.js -->
  <p class="ids__description">…</p>                          <!-- лид -->
  <ids-nav-item id="слаг-раздела" label="Название раздела">
    <h2 class="h3">…</h2>
    …
  </ids-nav-item>
  <div class="ids__space L"></div>
</article>
```

Правила структуры:

- **Фронтматтер** — значения с двоеточием (`description: "Алгоритм: 3 шага"`) в кавычках: YAML иначе не разбирается.
- **Разделы** — `<ids-nav-item id label>`, оглавление строится из них само. Якорь раздела — осмысленный слаг (`#small-formats`), не порядковый номер (`#n0`, как на старом сайте): номера ломаются при вставке раздела в середину.
- **Уровни заголовков** — три: `h1` — название публикации (одно), `h2` — раздел (попадает в оглавление; обычно `h2.h3` — мельче), `h3` — подраздел внутри раздела. Глубже не используется.
- **Отступы** — у заголовка верхнее поле своё и заметно больше нижнего; спейсер `ids__space` (S) прямо перед `h2`/`h3`/`ids-nav-item` схлопывается в ноль, ставить его незачем. Крупные M/L/XL работают как есть.
- **Nunjucks внутри HTML-комментариев исполняется** — незакрытый `{% %}` в комментарии роняет сборку.
- **Ссылка на любое место** появляется сама: `js/anchor.js` раздаёт блокам тела статьи id вида `слаг-раздела-хэш` по хэшу содержимого (иконка-цепь слева от блока копирует URL, переход подсвечивает блок). Размечать ничего не нужно. Следствие: правка текста блока меняет его id, старые ссылки на абзац ведут к началу страницы; id у `h2` из `ids-nav-item` стабильны.

**Данные.** У каждой публикации — запись в `src/data/publications.js` (таблица на главной и мета-блок под h1 берут оттуда заголовок, дату и теги). Поля:

- `authors` — слаги из `src/data/authors.js`. Новый автор заводится там: имя, слаг, фото в `static/images/authors/`.
- `contact` — оунер публикации, помечается в мета-блоке. Если на исходной странице оунера нет — `null`; первый автор оунером не назначается.
- `status` — `"published"`. У неперенесённых гайдов стоит `"stub"` и страница-заглушка: при переносе заглушка перезаписывается, статус меняется.

## Компоненты и стили

Разметка собирается только из компонентов IDS — их перечень с образцами на `/design-system/`. Локальные компоненты живут в `static/css/components/` с префиксом `ids__` и подключаются в `src/includes/layout.html`. Внутри компонента размеры в `em` (масштабируются от кегля), на уровне композиции — в `rem`. Цвет — только через семантические токены (`--ids__text`, `--shift__brand`); новое значение сперва заводится в палитре `tokens/palette.css`, потом получает семантическое имя в `tokens/colors.css` или `tokens/shift.css`.

**Page-local стилей нет.** `<style>` в публикации не пишется — ни для «специфичной таблицы», ни для «одного раза». Всё, что нужно странице, становится каноничным компонентом или модификатором существующего и получает образец на `/design-system/`. Компонент проверяется один раз на витрине; в публикации проверяются только отступы между блоками. Если исходная страница делает то, под что компонента нет, порядок такой:

1. CSS компонента или модификатора в `static/css/components/` (новый файл — подключить в `layout.html`).
2. Блок на витрине: мета-табличка (классы, токены) → образец на всю ширину → список использований.
3. Разметка в публикации.

**На витрине — только компоненты публикаций.** Компоненты сайта (шапка, поиск, переключатель языка, таблица и фильтры публикаций, промо-плашки главной, блок «Люди», якоря-цепочки) на `/design-system/` не выводятся. Образец компонента — живой фрагмент публикации: текст, картинки и ссылки берутся из реальной страницы, где компонент используется, а не сочиняются; у образца с несколькими состояниями (метки «Нет/Да», отмеченный чекбокс) состояния показываются на том же реальном материале. Компонент, у которого список использований пуст, с витрины убирается.

**Список использований** строит фильтр `usages` на сборке: последняя строка блока `.guide-component` — `{{ ".ids__slide-pair" | usages | safe }}` (селектор — класс, `tag.class` или кастомный элемент; несколько через запятую). Страница, где компонент встречается один раз, даётся якорной ссылкой на раздел, где несколько раз — адресом страницы. «Пока не используется» — сигнал: компонент либо ждёт своего гайда, либо подлежит удалению. Фильтр читает `src/pages/*.html` при старте сборки: после правки `eleventy.config.js` дев-сервер перезапускается.

**Модификаторы в CSS** — полными селекторами (`.ids__no-yes.under`), не конкатенацией `&---mod`: нативный нестинг её не поддерживает, и правило молча не применяется (пример — [no-yes.css](../static/css/components/no-yes.css)).

**Инлайн-блоки `.ids__no-yes`** склеиваются комментарием `</div><!--\n  --><div…`: пробел между ними считается за ширину и ломает строку.

**Ширины.** У медиа-компонентов фиксированный ряд размеров (XXS…XL). Нестандартная ширина исходника (например, 22em на старом сайте) не воспроизводится — округляется до ближайшего размера IDS (M = 20em). Новый размер добавляется в ряд, только если ближайший ломает смысл картинки.

## Картинки

Картинки лежат в `static/images/<slug>/`, путь в разметке — `/images/<slug>/…`. Внешние URL (Cloudinary и прочие) остаются внешними.

**Путь к файлу не собирается шаблоном** (`src="/images/x/{% if lang == 'ru' %}1.jpg{% else %}1-en.jpg{% endif %}"`): оптимизатор такие пути не видит и не правит. Внутри `{% if %}` дублируется весь тег целиком.

**Оптимизация до коммита.** Материалы приходят неадекватными по весу: фотографии по 6000 px, которые рисуются в 460, фото в PNG, GIF-анимации по 8 МБ. Порядок:

```
npm run build
python3 -m http.server 8091 --directory site &   # нужен для замера
node tools/measure-images.mjs                    # с какой шириной что рисуется → tools/image-widths.json
python3 tools/optimize-images.py                 # ресайз + WebP + GIF → mp4; при переносе — с --no-originals
python3 tools/optimize-images.py --fix-links     # правит ссылки в разметке
npm run build
```

Что за этим стоит:

- целевая ширина — **2× от фактической ширины отрисовки** (ретина). Текстовая колонка 960 px, значит потолок для картинки во всю ширину — 1920 px, а для `figure.ids__media XS` (184 px) — 368 px;
- **WebP** для фото и скриншотов; палитровые PNG (плоская графика, интерфейс с малым числом цветов) часто уже легче WebP — такие скрипт оставляет;
- **GIF всегда переводится в mp4**: те же кадры весят в 10–15 раз меньше. `<img>` заменяется на `<video src="…" autoplay loop muted playsinline>`, в медиа-контейнерах IDS видео уже стилизовано как картинка;
- `tools/image-widths.json` — кэш замеров, в гитигноре: пересоздаётся перед каждым запуском оптимизатора.

**Исходники.** В репозиторий попадает только оптимизированный файл; исходник хранится рядом, но не коммитится:

- папка `originals/` в корне репозитория, структура повторяет `static/` (`originals/images/<slug>/…`). Она в `.gitignore` репозитория; на новой машине её нужно создать — оптимизатор создаёт сам при первом переносе;
- оптимизатор переносит оригинал туда вместо удаления. Картинка, пришедшая уже оптимизированной (WebP от автора), кладётся в `originals/` руками;
- при переносе со старого сайта исходники не хранятся — они есть в старом репозитории: оптимизатор запускается с `--no-originals`.

Оптимизатор проходит по всей `static/images/`, а не только по новой папке, и заодно ужимает чужие картинки, если им есть что ужать: перед коммитом `git status` сверяется с публикацией, лишнее откатывается. Фото авторов (`static/images/authors/`) он не трогает: на них ссылаются данные `authors.js`, а не разметка, `--fix-links` их бы не поправил.

## Перенос со старого сайта

Старый сайт — `/Users/arutyunov/dbdt` (Express + Pug + SCSS), контент вшит в Pug с миксинами `+ru`/`+en`. Список публикаций и их статусы — в CSV «Shift — All Guides», переносятся помеченные «Актуально».

Порядок:

1. `git pull` в dbdt: публикации правятся до последнего.
2. `node tools/pug-to-html.mjs <путь к .pug> --out <файл>` — страница прогоняется через Pug (нужен пакет `pug` в скретчпаде, см. шапку скрипта), на выходе HTML, где `+ru`/`+en` превращены в `{% if lang == 'ru' %}…{% else %}…{% endif %}`, пустой `+en` — в русский текст без условия, обвязка старого шаблона выброшена. Флаг `--ru-only` выбрасывает все `+en`. Текст не перенабирается: так он остаётся дословным, с неразрывными пробелами и опечатками исходника.
3. Старые классы перекладываются на компоненты по таблице соответствия; для чего компонента нет — сначала компонент на витрину.
4. Картинки копируются пофайлово — ровно те, на которые ссылается живая разметка. В папках старого сайта лежат черновики, отброшенные варианты и картинки прошлых редакций: `cp -R` приносит десятки мегабайт мусора.
5. Оптимизация с `--no-originals`, запись в `publications.js`, автор в `authors.js`, проверка.

Переносится **живой** контент страницы, дословно и целиком. Не переносится:

- закомментированные блоки Pug (`//` и `//-`) — в старых гайдах их много, иногда половина файла;
- теги тем, подборок, авторов, хлебные крошки, блоки «Читать далее» — таких сущностей на новом сайте нет;
- `+es` (испанская локаль) — не поддерживается;
- обвязка старого шаблона: `.guide-nav-wrapper`, `.guide-body-wrapper`, `.mobile-breadcrumbs`, `block topicTags/peopleTags`;
- page-local `style.` и `script.` старой страницы — вместо них компоненты.

Пустой `+en` означает «перевода нет»: русский текст без условия, английская страница показывает его же. Перевод и сокращения не делаются, опечатки исходника сохраняются. Отдельное решение «переносить без перевода» (как у «Визуального стиля Додо Пиццы») означает: все `+en` отбрасываются, текст без условий.

Битые внутренние ссылки исходника (`href="#n10"` на раздел, которого нет) ведутся на реальный слаг нужного раздела.

## Неразрывные пробелы

Текст новой публикации проходит через `node tools/nbsp.mjs <slug>` один раз, при вёрстке, до коммита: инструмент ставит неразрывные пробелы после коротких слов, перед тире и частицами, между числом и единицей (правила — [nbsp.md](nbsp.md)). Запускается только по прямому запросу или как шаг вёрстки нового материала; не автоматически, не по всем страницам и никогда между коммитом и публикацией. При переносе со старого сайта не запускается: текст из Pug уже типографирован.

## Проверка перед коммитом

```
npm run build                        # без ошибок
grep -l '<style>' src/pages/*.html   # новой страницы в списке быть не должно
```

Затем на локальном сервере:

1. Собрать все `href`/`src` со страниц и проверить, что локальные файлы существуют. Ссылки на ещё не перенесённые гайды в 404 — ожидаемо, всё остальное — нет.
2. Консоль браузера и 404 в сети.
3. RU и EN версии, мобильная ширина (< 768 px).
4. Новый компонент — на `/design-system/`; в публикации — только отступы.
5. Для новой публикации (не переноса): `node tools/nbsp.mjs <slug>` выполнен один раз.

`site/`, `originals/`, `tools/image-widths.json` в гитигноре; временные файлы в `static/` не остаются.
