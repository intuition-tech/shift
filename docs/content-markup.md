# Вёрстка публикаций

Инструкция для агента, который верстает публикацию на новом сайте или переносит её со старого. Общее устройство проекта — в [README](../README.md), живые образцы всех компонентов со списком классов и мест использования — на `/design-system/`.

## Структура публикации

Каждая публикация — один файл `src/pages/<slug>.html` с фронтматтером и инлайновым переключением языка. URL плоские: `/<slug>/` и `/en/<slug>/`.

```html
---
title: Название — Shift
titleEn: Title — Shift
description: "…"
tags: publication
---
<div class="ids__space XL"></div>
<article class="ids__wrapper publication">
  <div class="publication__nav"><ids-navbar></ids-navbar></div>   <!-- если есть разделы -->
  <h1>{% if lang == 'ru' %}…{% else %}…{% endif %}</h1>
  {% include "pub-meta.html" %}                              <!-- дата и теги из src/data/publications.js -->
  <p class="ids__description">…</p>                          <!-- лид -->
  <ids-nav-item id="слаг-раздела" label="Название раздела">
    <h2 class="h3">…</h2>
    …
  </ids-nav-item>
  <div class="ids__space L"></div>
</article>
```

Оглавление строится само из `<ids-nav-item>`. Якоря разделов — **осмысленные слаги** (`#small-formats`), не порядковые номера (`#n0`, как на старом сайте): номера ломаются при вставке раздела в середину.

**Уровни заголовков** — три: `h1` — название публикации (одно), `h2` — раздел (попадает в оглавление; обычно `h2.h3` — мельче), `h3` — подраздел внутри раздела. Глубже не используем. Поле сверху у заголовка своё и заметно больше нижнего — заголовок прижат к своему тексту; **спейсер `ids__space` (S) прямо перед `h2`/`h3`/`ids-nav-item` схлопывается в ноль**, ставить его не нужно (крупные M/L/XL остаются как есть).

**Ссылка на любое место.** Блокам тела статьи (заголовки, абзацы, списки, фигуры, таблицы, врезки, компоненты) `js/anchor.js` раздаёт id вида `слаг-раздела-хэш` по хэшу содержимого: из левой трети колонки над блоком появляется иконка-цепь, клик копирует URL с якорем, переход по нему подсвечивает блок. Размечать ничего не нужно; учитывайте только, что **правка текста блока меняет его id** — старые ссылки на этот абзац приведут к началу страницы (h2 с id из `ids-nav-item` стабильны). Не входят: h1, аннотация, мета-блок.

**Данные.** У каждой публикации — запись в `src/data/publications.js` (таблица на главной и мета-блок под h1 берут оттуда заголовок, дату и теги). Поля:

- `authors` — слаги из `src/data/authors.js`; нового автора заведите там (имя, слаг, фото в `static/images/authors/`);
- `contact` — оунер публикации, помечается в мета-блоке. Если на исходной странице оунера нет — `null`, не назначайте первого автора;
- `status` — `"published"`; у неперенесённых гайдов стоит `"stub"` и страница-заглушка, при переносе перезаписывайте её и меняйте статус.

## Компоненты и стили

Разметка собирается только из компонентов IDS — их перечень с образцами на `/design-system/`. Локальные компоненты живут в `static/css/components/` с префиксом `ids__` и подключаются в `src/includes/layout.html`. Внутри компонента размеры в `em` (масштабируются от кегля), на уровне композиции — в `rem`. Цвет — только через семантические токены (`--ids__text`, `--shift__brand`); новое значение сперва заводится в палитре `tokens/palette.css`, потом получает семантическое имя в `tokens/colors.css` или `tokens/shift.css`.

**Page-local стилей нет.** `<style>` в публикации не пишется — ни для «специфичной таблицы», ни для «одного раза». Всё, что нужно странице, становится каноничным компонентом или модификатором существующего и получает образец на `/design-system/`. Компонент проверяется один раз на витрине; в публикации проверяются только отступы между блоками. Если исходная страница делает что-то, под что компонента нет, порядок такой: сначала компонент на витрину (CSS, блок с мета-табличкой и образцом, список использований), потом разметка.

**Блок компонента на витрине** — `.guide-component`: мета-табличка (классы, токены) → образец на всю ширину → список использований. Список строит фильтр `usages` на сборке: последняя строка блока — `{{ ".ids__slide-pair" | usages | safe }}` (селектор — класс, `tag.class` или кастомный элемент; несколько через запятую). Страница, где компонент встречается один раз, даётся якорной ссылкой на раздел, где несколько раз — адресом страницы. Список намеренно мелкий и в колонках. «Пока не используется» — сигнал: компонент либо ждёт своего гайда, либо подлежит удалению.

**Ширины.** У медиа-компонентов фиксированный ряд размеров (XXS…XL). Нестандартную ширину исходника (например, 22em на старом сайте) не воспроизводите — округляйте до ближайшего размера IDS (M = 20em). Новый размер в ряд добавляется только если ближайший заметно ломает смысл картинки.

**Соответствие старых классов компонентам** (пополняется):

| Старый сайт | Новый сайт |
|---|---|
| `.link-button` «Смотреть файл» | `a.ids__promo-link` в своём абзаце |
| `.dodo-not-dodo` «Додо / Не Додо» | `.ids__sequence XL gap-M labels` |
| `.dodo-not-dodo--yes-green` «Нет / Да» | `.ids__sequence XL gap-M labels yes-green` |
| пара картинок с подписью под каждой (`.scale-example-pics`) | `.ids__sequence XL gap-M`, внутри `figure.ids__media.shadow` с `figcaption` |
| одиночная картинка во всю ширину (`.scale-example-pic--full`) | `.ids__media-group XL shadow` |
| `figure.shadow-img` | `.ids__media-group` / `.ids__media` с `.shadow` |

### Грабли

- **Нативный CSS-нестинг не умеет конкатенацию `&---mod`** — это привычка из Sass. Модификаторы с длинными суффиксами пишутся полными селекторами (см. [no-yes.css](../static/css/components/no-yes.css)); иначе правило молча не применяется.
- **Инлайн-блоки `.ids__no-yes` ставятся вплотную**: пробел между `</div>` и `<div>` считается за ширину и ломает строку. В разметке они склеиваются комментарием: `</div><!--\n  --><div…`.
- **YAML во фронтматтере**: значение с двоеточием (`description: Алгоритм: 3 шага`) роняет сборку — берите в кавычки.
- **`{% %}` исполняется и внутри HTML-комментариев** — незакрытый тег Nunjucks там сломает сборку.
- **Не собирайте путь к файлу шаблоном** (`src="/images/x/{% if lang == 'ru' %}1.jpg{% else %}1-en.jpg{% endif %}"`): такие пути не переживают автоматических замен при оптимизации картинок. Дублируйте внутри `{% if %}` весь тег целиком.
- **Атрибут `class` с шаблонной вставкой** (`class="x {% if … %}y{% endif %}"`) фильтр `usages` понимает, но держите вставку внутри атрибута, не вокруг всего тега.

## Картинки

Складывать в `static/images/<slug>/`, путь в разметке — `/images/<slug>/…`. Внешние URL (Cloudinary и прочие) оставляем внешними.

**Оптимизируйте до коммита.** Материалы приходят неадекватными по весу: фотографии по 6000 px, которые рисуются в 460, фото в PNG, GIF-анимации по 8 МБ. Порядок:

```
npm run build
python3 -m http.server 8091 --directory site &   # нужен для замера
node tools/measure-images.mjs                    # с какой шириной что рисуется → tools/image-widths.json
python3 tools/optimize-images.py                 # ресайз + WebP + GIF → mp4
python3 tools/optimize-images.py --fix-links     # правит ссылки в разметке
npm run build
```

Что за этим стоит:

- целевая ширина — **2× от фактической ширины отрисовки** (ретина). Текстовая колонка 960 px, значит потолок для картинки во всю ширину — 1920 px, а для `figure.ids__media XS` (184 px) — 368 px;
- **WebP** для фото и скриншотов, но палитровые PNG (плоская графика, интерфейс с малым числом цветов) часто уже легче WebP — скрипт такие оставляет, и это правильно;
- **GIF всегда переводится в mp4**: те же кадры весят в 10–15 раз меньше. `<img>` заменяется на `<video src="…" autoplay loop muted playsinline>`, в медиа-контейнерах IDS видео уже стилизовано как картинка;
- `--fix-links` не видит пути, собранные шаблоном, — их правят руками (см. грабли выше).

**Исходники храним, но не коммитим.** Оптимизатор не удаляет оригинал, а переносит его в `originals/<тот же путь, что в static/>` — папка в гитигноре. Из оригинала пересохраняют картинку под новый размер или возвращают исходник; в репозиторий попадает только оптимизированный файл. Если картинка пришла не через оптимизатор (например, уже в WebP от автора), положите её исходник в `originals/` руками. `tools/image-widths.json` — кэш замеров, тоже в гитигноре: он пересоздаётся перед каждым запуском оптимизатора.

Оптимизатор проходит по всей `static/images/`, а не только по новой папке: заодно подхватит и чужие картинки, если им есть что ужать. Перед коммитом проверьте `git status` и откатите то, что не относится к вашей публикации. Фото авторов (`static/images/authors/`) он не трогает: на них ссылаются данные `authors.js`, а не разметка, и `--fix-links` их бы не поправил.

## Перенос со старого сайта

Старый сайт — `/Users/arutyunov/dbdt` (Express + Pug + SCSS), контент вшит в Pug с миксинами `+ru`/`+en`. Перед переносом сделайте там `git pull`: публикации правятся до последнего. Список публикаций и их статусы — в CSV «Shift — All Guides», переносятся помеченные «Актуально».

Переносится **живой** контент страницы, дословно и целиком. Не переносится:

- закомментированные блоки Pug (`//` и `//-`) — в старых гайдах их много, иногда половина файла;
- теги тем, подборок, авторов, хлебные крошки, блоки «Читать далее» — таких сущностей на новом сайте нет;
- `+es` (испанская локаль) — не поддерживается;
- обвязка старого шаблона: `.guide-nav-wrapper`, `.guide-body-wrapper`, `.mobile-breadcrumbs`, `block topicTags/peopleTags`;
- page-local `style.` и `script.` старой страницы — вместо них компоненты (см. выше).

Пустой `+en` означает «перевода нет»: русский текст пишется без условия, английская страница показывает его же. Не переводите и не сокращайте сами — опечатки исходника тоже переносятся как есть. Отдельное решение «переносить без перевода» (как у «Визуального стиля Додо Пиццы») означает: все `+en` отбрасываются, текст без условий.

**Текст не перенабирайте — рендерите.** `node tools/pug-to-html.mjs <путь к .pug> --out <файл>` прогоняет страницу через Pug (нужен пакет `pug` в скретчпаде, см. шапку скрипта) и отдаёт HTML, где `+ru`/`+en` уже превращены в `{% if lang == 'ru' %}…{% else %}…{% endif %}`, пустой `+en` — в русский текст без условия, обвязка старого шаблона выброшена. Флаг `--ru-only` выбрасывает все `+en`. Дальше старые классы перекладываются на компоненты по таблице соответствия, но текст уже дословный, с неразрывными пробелами и опечатками исходника.

**Картинки копируйте пофайлово.** В папках старого сайта лежат черновики, отброшенные варианты и картинки прошлых редакций: при копировании папки целиком (`cp -R`) в репозиторий приезжают десятки мегабайт мусора. Копируйте ровно те файлы, на которые ссылается живая разметка.

**Битые внутренние ссылки исходника** (`href="#n10"` на раздел, которого нет) ведите на реальный слаг нужного раздела, не переносите как есть.

## Проверка перед коммитом

```
npm run build                    # без ошибок
grep -l '<style>' src/pages/*.html   # новой страницы в списке быть не должно
```

Затем на локальном сервере: собрать все `href`/`src` со страниц и проверить, что локальные файлы существуют; консоль браузера; 404 в сети; RU и EN версии; мобильная ширина (< 768 px). Новый компонент проверяется на `/design-system/`, в публикации — только отступы. Ссылки на ещё не перенесённые гайды в 404 — ожидаемо, всё остальное — нет.

Не коммитьте `site/`, `originals/`, `tools/image-widths.json` (все в гитигноре) и не оставляйте временные файлы в `static/`.
